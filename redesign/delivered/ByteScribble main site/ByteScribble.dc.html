Stream Processing

The Architecture of Apache Flink

A tour of the runtime: how your job graph is translated, scheduled, and kept consistent while the data never stops arriving.

HKHritik Kumar ·12 Jun 2026·18 min read

Why the architecture is the API

Most Flink tutorials start with DataStream and end with a word count. That teaches you the surface and leaves the interesting part — why the surface has that shape — completely dark. Flink's API constraints fall directly out of four runtime decisions: a dataflow graph of operators, pipelined shuffles, keyed state co-located with its partition, and asynchronous barrier snapshots.

Understand those four and you can predict how a job will behave under backpressure, why a keyed window can't see another key's state, and what actually happens in that pause before a checkpoint completes.

Batch is a bounded special case of streaming. Once you accept that, the checkpointing machinery stops looking like overhead and starts looking like the point.

From job graph to execution graph

Your program is a logical DAG. The client turns it into a JobGraph, chaining operators that can run in the same thread; the JobManager expands that into an ExecutionGraph with one vertex per parallel subtask. Chaining is the single biggest cheap win — a chained map/filter pair passes records by method call, not through a network buffer.

Java · FraudDetectionJob.java 
// One job, one keyed pipeline, exactly-once into Kafka.
final StreamExecutionEnvironment env =
    StreamExecutionEnvironment.getExecutionEnvironment();
env.enableCheckpointing(30_000, CheckpointingMode.EXACTLY_ONCE);
env.setParallelism(8);

DataStream<Transaction> txns = env
    .fromSource(kafkaSource, WatermarkStrategy
        .<Transaction>forBoundedOutOfOrderness(Duration.ofSeconds(5))
        .withTimestampAssigner((tx, ts) -> tx.eventTime()),
      "txn-source");

txns.keyBy(Transaction::accountId)
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .aggregate(new VelocityAggregate())
    .filter(v -> v.count() > 12 || v.total() > 50_000)
    .sinkTo(alertSink)
    .name("velocity-alerts");

env.execute("fraud-detection");
i

Note. setParallelism(8) is a default, not a promise. An operator's real parallelism is capped by available task slots; slot sharing then packs one subtask of every chained operator into a single slot, which is why a job with four stages at parallelism 8 still needs only 8 slots.

JobManager, TaskManagers, slots

The JobManager is the brain: it schedules subtasks, coordinates checkpoints, and reacts to failures. TaskManagers are the muscle — JVM processes that expose task slots and exchange records over a shared network stack of buffers. One JobManager per job (with HA standbys); as many TaskManagers as your capacity plan wants.

Component Owns Failure blast radius
JobManagerScheduling, checkpoint coordinationWhole job (HA failover)
TaskManagerSlots, network buffers, local stateIts subtasks → region restart
Task slotOne parallel slice of a chained pipelineOne key range

Keyed state lives with its partition

A keyBy hashes each key into one of maxParallelism key groups, and key groups are assigned to subtasks. State reads are therefore always local — RocksDB on the TaskManager's disk, or the JVM heap — and rescaling means shipping key groups, not rows.

SQL · equivalent in Flink SQL 
SELECT account_id,
       TUMBLE_START(event_time, INTERVAL '1' MINUTE) AS win_start,
       COUNT(*) AS txn_count,
       SUM(amount) AS total
FROM transactions
GROUP BY account_id, TUMBLE(event_time, INTERVAL '1' MINUTE)
HAVING COUNT(*) > 12 OR SUM(amount) > 50000;
⚠

Warning. maxParallelism is fixed at the first checkpoint and cannot be changed without discarding state. Set it deliberately (a few times your expected ceiling) before the job ever runs in production.

Barriers, not stop-the-world

The coordinator injects a numbered barrier into every source partition. Barriers flow with the records; when an operator has seen barrier n on all inputs it snapshots its state asynchronously and forwards the barrier. Processing never halts — only alignment waits, and unaligned checkpoints remove even that under backpressure.

What to remember

  • Chaining is free throughput; a network shuffle is not. Read the job graph in the UI before tuning anything.
  • State is local because keys are partitioned. Every "why can't I see that key here" question resolves to this.
  • Checkpoints buy you exactly-once; savepoints buy you upgrades. They are not the same artifact.
